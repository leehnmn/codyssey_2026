## 1. VPC 네트워크 4대 요소와 트래픽 흐름

AWS에서 가상 네트워크를 구축할 때 필수적으로 조합되는 4대 기본 구성 요소입니다:

```
[Internet]
    ↕
[Internet Gateway (IGW)]  : VPC와 외부 인터넷을 연결해주는 관문 (1:1 매핑)
    ↕
[Route Table (라우팅 테이블)] : 목적지 IP(CIDR)를 보고 어디로 패킷을 보낼지 결정하는 이정표
    ↕
[Subnet (서브넷)]         : VPC의 IP 대역을 특정 가용영역(AZ) 단위로 잘라 격리한 네트워크 구역
    ↕
[EC2 / ENI]              : 서브넷 내부에 배치되어 프라이빗 IP를 부여받은 가상 서버
```

### (1) VPC (Virtual Private Cloud)
- **개념**: AWS 클라우드 내에서 사용자의 계정 전용으로 논리적으로 격리된 가상 사설 네트워크입니다.
- **역할**: 외부 다른 AWS 고객의 자원과 네트워크 레벨에서 물리적/논리적으로 완전히 격리되며, 사설 IP 주소 범위(CIDR, 예: `10.0.0.0/16` - 총 65,536개 IP)를 직접 정의합니다.

### (2) Subnet (서브넷)
- **개념**: VPC의 CIDR 블록을 더 작은 조각으로 분할한 세부 네트워크 단위입니다.
- **특징**: 반드시 **단 하나의 가용 영역(Availability Zone, AZ)**에 종속됩니다.
- **Public Subnet vs Private Subnet 구분 기준**:
  - 서브넷에 연결된 라우팅 테이블에 **인터넷 게이트웨이(IGW)로 향하는 기본 경로(`0.0.0.0/0 -> igw-xxxx`)가 연결되어 있으면 Public Subnet**입니다.
  - 이 경로가 없고 내부 통신만 가능하거나 NAT Gateway로 향하면 **Private Subnet**입니다.
  - ⚠️ *주의: 서브넷 자체에 특별한 플래그가 있는 것이 아니라, '어떤 라우팅 테이블과 연결되어 있는가'가 퍼블릭/프라이빗을 결정합니다.*

### (3) Internet Gateway (인터넷 게이트웨이, IGW)
- **개념**: VPC와 공용 인터넷 사이의 양방향 통신을 가능하게 해주는 수평 확장형, 고가용성 소프트웨어 컴포넌트입니다.
- **핵심 역할 2가지**:
  1. VPC 라우팅 테이블에서 인터넷으로 나가는 트래픽의 목적지 타깃이 됩니다.
  2. **1:1 NAT(Network Address Translation) 변환**: EC2 인스턴스는 자신의 공인 IP를 알지 못하며 오직 사설 IP(`10.0.1.50`)만 가지고 있습니다. IGW가 인터넷으로 나갈 때 사설 IP를 공인 IP(`13.125.45.89`)로 변환하고, 들어올 때 공인 IP를 사설 IP로 변환해 줍니다.

### (4) Route Table (라우팅 테이블)
- **개념**: 서브넷 또는 게이트웨이에서 나가는 네트워크 트래픽의 방향을 결정하는 라우팅 규칙(Rule)들의 집합입니다.
- **동작 원리 (Longest Prefix Match)**:
  - 목적지 주소와 가장 길게 일치하는(가장 구체적인) CIDR 규칙을 우선 적용합니다.
  - 예: `10.0.1.50`으로 가는 트래픽은 `10.0.0.0/16 (local)`을 따르고, 네이버나 구글(`142.250.x.x`)로 가는 트래픽은 `0.0.0.0/0 (igw)`를 따릅니다.

## 2. Security Group vs NACL vs IAM의 본질적 차이

많은 초심자들이 보안 그룹(Security Group)과 IAM, 그리고 NACL(Network ACL)의 역할을 혼동합니다. 이 셋은 **방어하는 계층과 보호 대상**이 완전히 다릅니다.

| 비교 항목 | Security Group (보안 그룹) | Network ACL (NACL) | IAM (Identity & Access Mgmt) |
|:---|:---|:---|:---|
| **적용 레벨** | **인스턴스 / ENI 레벨** (가상 방화벽) | **서브넷 레벨** (경계 방화벽) | **AWS 계정 / API 호출 레벨** |
| **보호 대상** | EC2 인스턴스, RDS 등 컴퓨팅 자원 | 서브넷 경계를 넘나드는 모든 패킷 | AWS 서비스, 콘솔, API, CLI |
| **상태 유지** | **Stateful (상태 추적)** | **Stateless (상태 비추적)** | 해당 없음 (토큰/권한 평가) |
| **규칙 형태** | **허용(Allow) 규칙만 가능** (기본 All Deny) | **허용(Allow) 및 거부(Deny) 모두 가능** | 허용(Allow) 및 명시적 거부(Deny) |
| **규칙 평가** | 모든 규칙을 종합 평가하여 하나라도 허용되면 통과 | 규칙 번호 순서(낮은 번호 우선)로 순차 평가 | 명시적 Deny > Allow > Default Deny |
| **비유** | 아파트의 **개별 세대 현관문 도어락** | 아파트 단지 정문의 **차량 차단기** | 신분증 검사 및 출입증 발급 시스템 |

### 💡 Stateful(상태 추적)이란 무엇인가?
- 보안 그룹은 **Stateful**입니다. 즉, 인바운드 규칙에서 80번 포트를 허용하여 외부에서 요청이 들어왔다면, 해당 세션에 대한 **응답(Outbound) 트래픽은 아웃바운드 규칙에 별도로 명시하지 않아도 방화벽이 커넥션을 기억하고 자동으로 통과**시킵니다.
- 반면 NACL은 **Stateless**이므로, 들어오는 포트(Inbound 80)뿐만 아니라 나가는 임시 포트(Outbound Ephemeral Port: 1024~65535)까지 양방향을 모두 열어주어야 통신이 성립됩니다.

### 🛡️ 최소 권한 원칙(Principle of Least Privilege)의 적용
- **네트워크 최소 권한**:
  - 누구나 접속해야 하는 웹 서비스(HTTP:80)는 `0.0.0.0/0`을 열어주지만, 서버 관리용 포트인 SSH(22)는 절대 전체 개방하지 않고 **관리자의 공인 IP(`/32`)만 한정**하여 무차별 대입 공격(Brute Force)을 원천 차단합니다.
- **IAM 최소 권한**:
  - 실습용 사용자/Role에게 모든 권한을 가진 `AdministratorAccess`를 주지 않고, 오직 이번 실습에 필요한 `ec2:RunInstances`, `ec2:CreateVpc`, `ec2:AuthorizeSecurityGroupIngress` 등의 액션만 지정하고, S3나 RDS, 결제 정보 등 불필요한 영역은 배제합니다.

## 3. 외부 요청 패킷이 EC2 Nginx까지 도달하는 전체 여정

사용자가 스마트폰이나 노트북 브라우저에 `http://13.125.45.89`를 입력하고 엔터를 눌렀을 때, 전기 신호와 패킷이 Nginx 소켓까지 도달하는 7단계 여정입니다:

```
[1. User Client Browser] 
       │ (TCP SYN 패킷 전송: Dst IP 13.125.45.89, Dst Port 80)
       ▼
[2. Public Internet Routing (BGP)] 
       │ AWS 백본 네트워크 진입
       ▼
[3. AWS Internet Gateway (IGW)]
       │ 1:1 NAT 변환: Dst Public IP(13.125.45.89) → Dst Private IP(10.0.1.50)
       ▼
[4. VPC Route Table]
       │ 로컬 CIDR 10.0.0.0/16과 매칭 확인 후 Public Subnet으로 전달
       ▼
[5. Subnet Network ACL (NACL)]
       │ 인바운드 규칙 검사 (Default Allow: 0.0.0.0/0 Port 80 PASS)
       ▼
[6. Security Group (sg-web-access)]
       │ 인스턴스 ENI 앞단에서 패킷 검사: TCP Port 80 허용 규칙 확인 -> PASS!
       ▼
[7. EC2 Linux Kernel & Nginx]
       │ 커널 TCP/IP 스택 -> iptables -> Nginx Listen 소켓 (0.0.0.0:80) 수락
       ▼
[Response 반환]
       │ Nginx가 HTTP 200 OK 패킷 생성 
       │ (Security Group이 Stateful이므로 아웃바운드 자동 통과 -> IGW에서 Public IP 변환 -> 유저 브라우저 도착)
```

이 흐름 중 단 하나라도(IGW 라우팅 누락, 퍼블릭 IP 미할당, 보안 그룹 80번 차단, Nginx 프로세스 다운) 어긋나면 외부 접속은 실패합니다.

## 4. 엔지니어다운 트러블슈팅 사고방식과 로그 분석 기법

문제가 발생했을 때 초보자는 설정을 무작위로 변경(Trial & Error)하지만, 숙련된 엔지니어는 **에러 메시지와 패킷 거동의 차이**를 통해 장애 지점을 좁힙니다.

### Connection Timed Out vs Connection Refused의 결정적 차이
1. **`Connection Timed Out` (응답 없음/타임아웃)**:
   - **의미**: 클라이언트가 보낸 TCP SYN 패킷에 대해 상대방으로부터 SYN+ACK도, RST도 전혀 오지 않고 중간에서 증발(Drop)함.
   - **의심 지점**: **네트워크 레벨 장애** (보안 그룹 인바운드 누락, 서브넷 라우팅 테이블 IGW 누락, NACL 차단).
2. **`Connection Refused` (연결 거부)**:
   - **의미**: 패킷이 EC2 인스턴스의 OS 커널까지 무사히 도달했으나, 해당 포트(80)를 열고 대기(Listen) 중인 프로세스가 없어서 OS 커널이 즉시 RST(Reset) 패킷을 회신함.
   - **의심 지점**: **소프트웨어 레벨 장애** (Nginx 프로세스가 죽어있거나 시작되지 않음, 포트 바인딩 설정 오류).

### 로그 분석 필수 명령어 3선
1. **Nginx 에러 및 액세스 로그 실시간 추적:**
   ```bash
   sudo tail -f /var/log/nginx/access.log /var/log/nginx/error.log
   ```
2. **systemd 서비스 상태 및 저널 로그 확인:**
   ```bash
   sudo systemctl status nginx
   sudo journalctl -u nginx -n 50 --no-pager
   ```
3. **포트 수신 대기(Listen) 소켓 점검:**
   ```bash
   sudo ss -tlpn | grep :80
   # 출력에 nginx가 0.0.0.0:80으로 떠 있어야 함
   ```

## 5. 클라우드 과금 구조와 안전한 리소스 회수 원칙

클라우드에서 비용이 발생하는 대표적인 4가지 축은 **Compute(컴퓨팅), Storage(스토리지), Networking(네트워크 전송량), Idle Reserved(유휴 예약 자원)**입니다.

| 과금 요소 | 발생 조건 | 프리티어 범위 | 방치 시 과금 위험 |
|:---|:---|:---|:---|
| **EC2 컴퓨팅** | 인스턴스가 `Running` 상태인 시간 | 월 750시간 (t2.micro / t3.micro) | 여러 대 생성 시 한도 초과 |
| **EBS 스토리지** | 볼륨이 **생성되어 존재하는 용량(GB-월)** | 월 30 GB (gp2 / gp3) | **인스턴스를 중지(Stop)해도 볼륨 비용은 24시간 청구됨** |
| **탄력적 IP (EIP)**| EIP가 할당되었으나 **실행 중인 인스턴스에 미연결(Idle) 시** | 실행 중인 1개 인스턴스 연결 시 무료 | 미연결 방치 시 시간당 약 $0.005 청구 |
| **NAT Gateway** | 생성되어 존재하는 시간 및 데이터 처리량 | **프리티어 없음!** | 시간당 약 $0.059 + 데이터 비용 (월 약 4~5만원) |

### 안전한 정리 순서 원칙: "종속성 역순 삭제"
EC2 인스턴스를 Terminate할 때 루트 볼륨의 **`DeleteOnTermination: true`** 설정을 확인해야 인스턴스 종료와 함께 디스크가 자동 삭제됩니다. 인스턴스가 삭제된 후에는 남아있는 EIP 릴리스, 보안 그룹, 라우팅 테이블, 인터넷 게이트웨이, 서브넷, VPC 순서로 깔끔하게 정리합니다.

## 6. 실전 대비: 예상 기술 질문 및 모범 답변 5선

### Q1. "VPC에서 서브넷을 생성했는데, 이 서브넷이 Public 서브넷인지 Private 서브넷인지 어떻게 구분하고 결정하나요?"
> **답변:**  
> "서브넷 자체의 설정값으로 구분되는 것이 아니라, **해당 서브넷과 연결된 라우팅 테이블(Route Table)에 인터넷 게이트웨이(IGW)로 향하는 기본 경로(`0.0.0.0/0 -> igw-xxxx`)가 정의되어 있는가**로 결정됩니다. 인터넷 게이트웨이 경로가 연결되어 있고 인스턴스에 퍼블릭 IP가 할당되면 Public 서브넷이 되며, 내부 통신 경로만 있거나 NAT Gateway로 향하면 Private 서브넷이 됩니다."

### Q2. "EC2 인스턴스 보안 그룹에서 인바운드 80 포트를 열었습니다. 클라이언트가 웹 페이지를 요청해서 데이터를 받아가려면 아웃바운드 규칙에도 임시 포트나 80 포트를 열어줘야 하나요?"
> **답변:**  
> "열어주지 않아도 정상 통신됩니다. 보안 그룹(Security Group)은 **상태 추적(Stateful)** 방화벽이기 때문입니다. 인바운드 규칙에 의해 허용된 트래픽에 대한 회신(Response) 패킷은 아웃바운드 규칙에 상관없이 커넥션 테이블에 의해 자동으로 허용되어 반환됩니다. 만약 서브넷 단위의 Stateless 방화벽인 NACL을 사용한다면 아웃바운드 임시 포트(Ephemeral Ports: 1024~65535)를 열어주어야 합니다."

### Q3. "웹 브라우저로 EC2 퍼블릭 IP에 접속했는데 `Connection Timed Out` 에러가 발생했습니다. 가장 먼저 무엇을 확인하고 어떻게 접근하시겠습니까?"
> **답변:**  
> "`Connection Timed Out`은 패킷이 대상 소켓에 닿지 못하고 중간 네트워크에서 드롭(Drop)되고 있음을 의미합니다.  
> 저는 가장 먼저 **(1) EC2에 연결된 보안 그룹의 인바운드 규칙에 80번 포트가 0.0.0.0/0으로 열려있는지** 확인하고,  
> **(2) 해당 서브넷의 라우팅 테이블에 0.0.0.0/0 -> IGW 경로가 누락되지 않았는지**,  
> **(3) SSH로 접속하여 Nginx 데몬이 실제로 실행 중이며 80번 포트에서 LISTEN 상태인지** 점검하겠습니다. 만약 프로세스가 죽어있다면 `Connection Refused`가 발생하므로, 타임아웃은 보안 그룹이나 라우팅 문제일 확률이 매우 높습니다."

### Q4. "SSH 포트(22)를 `0.0.0.0/0`으로 열어두면 왜 위험하며, 최소 권한 원칙을 어떻게 적용하셨나요?"
> **답변:**  
> "22번 포트가 전 세계(0.0.0.0/0)에 노출되면 수많은 봇넷과 악의적 공격자로부터 무차별 대입 공격(Brute Force)과 알려진 취약점 스캐닝의 표적이 됩니다. 실습 환경에서는 **관리자 개인의 공인 IP(`My IP /32`) 대역만 허용**하도록 보안 그룹 인바운드 규칙을 한정하여 공격 표면(Attack Surface)을 최소화했습니다. 프로덕션 환경이라면 Bastion Host를 구성하거나 AWS Systems Manager Session Manager를 도입하여 22번 포트를 인바운드에서 아예 닫는 방식을 채택할 수 있습니다."

### Q5. "EC2 인스턴스를 '중지(Stop)'시켜 놓으면 과금이 완전히 멈추나요?"
> **답변:**  
> "아닙니다. 인스턴스를 Stop하면 vCPU 및 RAM에 대한 컴퓨팅 시간 과금은 중단되지만, **인스턴스에 부착된 EBS 루트 볼륨(디스크 스토리지)은 데이터를 보존하고 있으므로 프로비저닝된 용량(GB-월)에 대한 스토리지 과금이 지속적으로 발생**합니다. 또한 연결되어 있던 탄력적 IP(Elastic IP)가 유휴(Idle) 상태가 되어 시간당 추가 페널티 비용이 발생할 수 있습니다. 따라서 실습이 완전히 끝났다면 반드시 **인스턴스 종료(Terminate)**를 수행하고 잔여 볼륨과 미사용 EIP를 완벽히 릴리스해야 합니다."
