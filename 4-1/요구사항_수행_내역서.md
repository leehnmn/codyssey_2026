## 1. 개요 및 최종 산출물 요약

본 내역서는 다중 사용자 환경에서의 권한 분립, 네트워크 기본 보안(SSH 강화 및 UFW 방화벽), 데몬 애플리케이션의 정상 기동 환경 검증, 그리고 시스템 리소스 관제 및 로그 관리를 자동화하는 쉘 스크립트(`monitor.sh`)의 구현 및 실증 결과를 정리한 문서입니다.

### 산출물 파일 구성
- `요구사항_수행_내역서.md`: 본 문서 (수행 내역, 증빙 자료, 명령어 기록, 개념 해설)
- `monitor.sh`: 시스템 관제 자동화 쉘 스크립트 (Health Check, 리소스 수집, 로테이션)
- `agent_app.py`: 5단계 Boot Sequence 및 TCP 15034 리슨 데몬 애플리케이션
- `report.sh` [보너스 1]: `monitor.log` 분석 및 통계 요약 리포트 스크립트
- `retention.sh` [보너스 2]: 시간 기반(7일 압축, 30일 삭제) 로그 보존 관리 스크립트
- `setup.sh`: 전체 사용자/그룹/디렉토리/환경 변수 자동 프로비저닝 스크립트
- `README.md`: 프로젝트 안내 및 퀵스타트 가이드

### [Step 1] 기본 보안 및 네트워크 설정

#### 1.1 SSH 포트 변경 및 Root 로그인 차단
- **설정 파일**: `/etc/ssh/sshd_config` (또는 `/etc/ssh/sshd_config.d/custom.conf`)
- **반영 설정**:
  ```text
  Port 20022
  PermitRootLogin no
  PasswordAuthentication yes
  ```
- **서비스 재시작 및 검증 명령어**:
  ```bash
  sudo systemctl restart ssh
  sudo sshd -T | grep -E 'port|permitrootlogin'
  sudo ss -tulnp | grep sshd
  ```
- **실제 검증 출력 증빙**:
  ```text
  $ sudo sshd -T | grep -E 'port|permitrootlogin'
  port 20022
  permitrootlogin no

  $ sudo ss -tulnp | grep sshd
  tcp   LISTEN 0      128          0.0.0.0:20022      0.0.0.0:*    users:(("sshd",pid=1024,fd=3))
  tcp   LISTEN 0      128             [::]:20022         [::]:*    users:(("sshd",pid=1024,fd=4))
  ```

#### 1.2 UFW 방화벽 정책 구성
- **보안 원칙**: 기본 모든 인바운드 차단(Default Deny), 필수 서비스(SSH 20022, APP 15034)만 인바운드 허용.
- **수행 명령어**:
  ```bash
  sudo ufw default deny incoming
  sudo ufw default allow outgoing
  sudo ufw allow 20022/tcp comment 'SSH Custom Port'
  sudo ufw allow 15034/tcp comment 'Agent App Port'
  sudo ufw --force enable
  sudo ufw status verbose
  ```
- **실제 검증 출력 증빙**:
  ```text
  $ sudo ufw status verbose
  Status: active
  Logging: on (low)
  Default: deny (incoming), allow (outgoing), disabled (routed)
  New profiles: skip

  To                         Action      From
  --                         ------      ----
  20022/tcp                  ALLOW IN    Anywhere                   # SSH Custom Port
  15034/tcp                  ALLOW IN    Anywhere                   # Agent App Port
  20022/tcp (v6)             ALLOW IN    Anywhere (v6)              # SSH Custom Port
  15034/tcp (v6)             ALLOW IN    Anywhere (v6)              # Agent App Port
  ```

## 5. 핵심 학습 목표 6대 문답 (평가 및 인터뷰 대비)

### Q1. SSH 포트 변경과 Root 원격 접속 차단이 왜 기본 보안의 핵심인가?
- **공격 자동화(봇넷) 차단**: 전 세계 해커들의 무차별 대입 공격(Brute-Force) 및 포트 스캔 봇은 기본 포트인 **22번**과 최고 관리자 계정인 **root**를 표적으로 삼습니다.
- **공격 표면 축소**: SSH 포트를 잘 알려지지 않은 고유 번호(예: `20022`)로 변경하는 것만으로도 자동화된 스캐너의 99% 이상을 무력화할 수 있으며, `PermitRootLogin no`를 적용하면 관리자 권한을 탈취하기 위해 일반 사용자 계정 침투 $\to$ `sudo` 권한 승격이라는 2중 방어선을 강제할 수 있습니다.

### Q2. “필요 포트만 허용”하는 방화벽(UFW) 정책 구성 원리와 검증법
- **기본 차단 원칙 (Default Deny)**: 외부로부터 들어오는 모든 인바운드 트래픽을 기본적으로 차단(`default deny incoming`)하고, 인가된 비즈니스 포트(`20022/tcp`, `15034/tcp`)만 화이트리스트 방식으로 개방합니다.
- **검증법**: `sudo ufw status verbose`로 활성화 상태 및 규칙 목록을 확인하며, 외부 클라이언트에서 열린 포트와 닫힌 포트에 대해 `nc -zv <IP> 20022` 및 `nc -zv <IP> 80`을 수행하여 닫힌 포트가 타임아웃 또는 드롭되는지 검증합니다.

### Q3. 역할 기반 계정/그룹과 ACL로 공유와 보안 디렉토리를 분리하는 이유
- **최소 권한의 원칙 (PoLP)**: 개발자(`agent-dev`)나 QA 테스터(`agent-test`)가 시스템 전체 권한이나 비밀 API 키에 접근할 수 있으면 내부 보안 위협이나 실수에 의한 장애 위험이 커집니다.
- **접근 통제**: 일반 파일(`upload_files`)은 전체가 속한 `agent-common` 그룹에 개방하여 협업을 보장하되, 민감 자산(`api_keys`, `/var/log/agent-app`)은 운영자/개발자 그룹인 `agent-core` 전용으로 제한하고 권한을 `2770`/`2775`로 묶어 `agent-test`의 접근을 완벽히 격리합니다.

### Q4. 환경 변수(`AGENT_HOME` 등)로 실행 환경을 고정하는 이유와 검증 방법
- **환경 독립성 및 일관성**: 디렉토리 경로나 포트 번호를 코드 내에 하드코딩하면 배포 경로가 바뀌거나 다중 서버 환경 구성 시 코드를 매번 수정해야 합니다.
- **검증 방법**: `agent_app.py` 기동 시 `os.environ.get()`을 통해 필수 환경 변수(`AGENT_HOME`, `AGENT_PORT`, `AGENT_KEY_PATH` 등)의 존재 여부와 유효성을 Boot Sequence 2단계에서 엄격히 검사하고, 하나라도 누락되면 즉각 기동을 중단함으로써 잘못된 환경에서의 비정상 동작을 사전에 차단합니다.

### Q5. 쉘 스크립트로 상태를 수집하고 로그로 남겨 운영 문제를 추적하는 흐름
- **장애 인지 및 골든 타임 확보**: 사람이 24시간 화면을 볼 수 없으므로, 쉘 스크립트가 1분마다 `pgrep`(프로세스), `ss`(포트), `top/free/df`(자원)를 점검하여 서비스 생존 여부를 주기적으로 판정합니다.
- **사후 분석의 토대**: `[타임스탬프] PID CPU MEM DISK` 형태의 정형화된 로그를 남김으로써 장애 발생 시 "장애 직전에 CPU가 치솟았는지, 메모리 누수가 발생했는지, 디스크가 가득 찼는지"를 데이터에 기반하여 명확하게 원인 분석(RCA)할 수 있습니다.

### Q6. crontab 주기 실행과 로그 보존 정책(압축/삭제)이 왜 필수적인가?
- **주기 실행의 당위성**: `cron` 데몬은 운영체제 레벨의 안정적인 스케줄러로, 서버가 재부팅되거나 장기 운영되더라도 정해진 주기에 맞추어 관제 스크립트를 누락 없이 실행시킵니다.
- **로그 보존 정책의 필수성**: 로그를 무제한으로 방치하면 디스크 용량이 100%에 도달하여 데이터베이스나 전체 OS가 다운되는 2차 대형 장애(Disk Full Outage)가 발생합니다. 따라서 `monitor.log`의 10MB 크기 단위 로테이션과, 7일 경과 파일의 `gzip` 압축 아카이빙, 30일 경과 파일의 자동 삭제 주기를 적용하여 디스크 사용량을 일정 수준으로 유지해야 합니다.
